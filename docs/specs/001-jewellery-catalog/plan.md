## Стек

| Область | Выбор | Причина |
| --- | --- | --- |
| Основа | React + TypeScript + Vite | Уже есть в проекте; статическое приложение. |
| UI | Mantine core/hooks — согласовано | Готовые компоненты и централизованная тема; собственное оформление шкатулки. |
| Формы | @mantine/form — согласовано | Одна система управления формами, включая динамические поля. |
| Стили | CSS Modules + семантические CSS variables | Свой спокойный фотокаталог и общая тема. |
| Данные | Dexie + dexie-react-hooks поверх IndexedDB | Транзакции, миграции, реактивные локальные запросы; без Dexie Cloud. |
| Проверка внешних данных | Zod | Проверка манифеста импорта и значений динамических полей во время выполнения. |
| PWA | vite-plugin-pwa, generateSW, обновление с предложением пользователю | Кэш оболочки, локальные ресурсы, управляемое обновление. |
| Архив | fflate, предварительный выбор | ZIP с JSON и оригиналами; до фиксации проверить память на iPhone и больших фото. |
| Проверки | Vitest, Testing Library, fake-indexeddb; Playwright для основных сценариев | Проверки поведения, транзакций и браузерных сценариев. |
| Качество | TypeScript strict, ESLint, Prettier | Проверяемые единые правила. |

Не добавлять пока глобальный state manager, второй UI-kit или отдельную библиотеку запросов. Долговечные данные живут в IndexedDB; состояние формы и фильтров — локально в React. Маршрутизацию выбрать при реализации навигации, исходя из требований статического хостинга.

Версии пакетов подбираются при установке по совместимости с фактическими React, TypeScript и Vite проекта и фиксируются lock-файлом. Наличие версии в package.json само по себе не доказывает совместимость будущих зависимостей.

## Структура

```text
src/
  app/                 # точка сборки, провайдеры, навигация, тема
  features/
    catalog/           # коллекция, карточка, фильтры
    item-editor/       # форма украшения и фотографии
    field-settings/    # определения пользовательских полей
    backup/            # импорт и экспорт
    settings/          # оформление и настройки
  domain/              # модели, схемы, правила без зависимости от React
  data/                # база, миграции, репозитории
  shared/              # только реально общие UI и утилиты
```

UI вызывает операции слоя данных; не открывает таблицы Dexie напрямую. Реактивные запросы инкапсулируются в hooks слоя данных. Не строить универсальную платформу форм: поддержать согласованные типы полей и стабильные ID. Шаблон создания содержит общие поля и поля по типам изделий. Предлагается сохранять независимый снимок схемы в каждой карточке, чтобы изменения шаблона не меняли существующие украшения.

## Тема — первый этап UI

- Один MantineProvider в корне. Светлая молочная и тёмная коричневая палитры, режим auto по умолчанию. Акценты: приглушённый бордовый (по умолчанию), зелёный и охра. Простой читаемый шрифт для всего интерфейса.
- Семантические токены: фон, поверхность, основной/вторичный текст, граница, акцент, ошибка, фокус; единые отступы, радиусы и типографика.
- Конкретные значения цветов задаются только в модуле темы. Компоненты используют токены.
- Уточнение архитектуры по аудиту: переносимые настройки оформления хранить в IndexedDB как источник истины и восстанавливать одной транзакцией с коллекцией. localStorage использовать только как производный кэш для первого отображения, синхронизировать после чтения базы и после импорта. Отказ обновления кэша не должен терять настройки или делать восстановление данных частичным. В задаче 01 доступ к настройкам изолировать, подключение канонического хранилища завершить в задаче 02.
- Проверить контраст и все состояния для каждой поддержанной комбинации темы и акцента.
- Сначала каркас и демонстрация полей/кнопок/диалогов в обеих темах, затем функциональные экраны.
- Навигация — сайдбар с коллекцией, подкатегориями и настройками. Основная версия мобильная, также базовый адаптив для десктопа. Предложение для прототипа: выдвижное меню на мобильном, постоянная панель слева на широком экране. В коллекции закрываемая плашка установки, в настройках постоянная ссылка на инструкцию.

## Данные и фотографии

Карточки и Blob фотографий хранятся отдельно в IndexedDB. Метаданные коллекции читаются без массовой загрузки оригиналов. Фото подгружаются по мере появления в области просмотра; object URL освобождаются. На первом этапе не создавать уменьшенные копии без отдельного согласования. Проверить память при работе с оригиналами на телефоне.

Сохранение/удаление записи с фото — транзакция. Все миграции версионируются; обновление приложения не удаляет базу. Ошибки квоты и доступа к хранилищу обрабатываются явно.

Перед изменением схемы написать проверку миграции с предыдущей версии. Не допускать молчаливой потери изменений при одновременном редактировании в двух вкладках; механизм проверки ревизии выбрать при реализации слоя данных.

## Импорт и экспорт

Предложение: manifest.json с formatVersion и метаданными плюс photos/<id> в ZIP. Полная проверка структуры, уникальности ID, ссылок, типов, размеров распаковки и версии до записи. Лимиты определить по измерениям на iPhone, не вводить молча. Замена базы выполняется одной транзакцией после подтверждения. Проверить экспорт→импорт сравнением данных и байтов фото.

Экспортировать согласованный снимок, чтобы изменение/удаление карточки во время подготовки архива не оставило потерянных ссылок на фото. Во время замены исключить конкурирующие записи. Отказ квоты должен откатывать замену вместе с переносимыми настройками. После восстановления сбросить производные UI-кэши, не относящиеся к новой коллекции. Проверять отмену системного сохранения файла и не объявлять её успешным экспортом без подтверждения доступного API.

Согласован сценарий переноса на другой телефон через полное восстановление с заменой текущих данных; объединение не требуется. Экспорт не меняет исходную коллекцию. При непустом целевом хранилище явно сообщать о замене и запрашивать подтверждение. Резервная копия включает текущий шаблон создания и снимки схем всех старых карточек. ZIP-библиотеку загружать при использовании экспорта/импорта. Способ сохранения и открытия файлов проверить через системный интерфейс iOS; не полагаться только на File System Access API. Проверить перенос между двумя устройствами, а также отмену и восстановление поверх непустой коллекции.

## PWA и проверка платформы

Все необходимые ресурсы поставляются с приложением, без внешних шрифтов/CDN. Service worker кэширует оболочку; пользовательская коллекция хранится в IndexedDB. Офлайн-готовность показывается после завершения подготовки. Не выполнять автоматический reload с несохранённой формой.

Playwright WebKit полезен для автоматизации, но не заменяет Safari и установленную PWA на iPhone. На устройстве проверить установку, авиарежим, закрытие/повторный запуск, камеру, фото из галереи, экспорт в «Файлы», восстановление, клавиатуру и обновление приложения.
