Не добавлять пока глобальный state manager, второй UI-kit или отдельную библиотеку запросов. Долговечные данные живут в IndexedDB; состояние формы и фильтров — локально в React. Задача 01 использует hash-маршруты `#/collection` и `#/settings`, чтобы прямые ссылки и перезагрузка работали без серверного rewrite на статическом хостинге. Сборка Vite задаёт минимум Chrome 111, Firefox 113 и Safari 16.2 по используемому `color-mix()`; фактическая проверка на целевых устройствах остаётся открытой.

Версии установленных пакетов фиксируются lock-файлом. Для Vite 8 требуется Node.js `^20.19.0` или `>=22.12.0`. Mantine 8.3.18, React 19.3.1 и TypeScript 6.0.3 совместно проверяются командами build, lint и test.

## Структура

```text
src/
  app/                 # точка сборки, провайдеры, маршруты и глобальная тема
  pages/               # страницы коллекции и настроек
  widgets/             # сайдбар, галерея и панели
  features/            # фильтрация, настройки оформления, инструкция
  entities/            # украшение и карточка
  shared/              # типы настроек и браузерные утилиты
  data/                # база, миграции и репозитории (задача 02)
```

UI вызывает операции слоя данных; не открывает таблицы Dexie напрямую. Реактивные запросы инкапсулируются в hooks слоя данных. Не строить универсальную платформу форм: пользовательские поля только текстовые, встроенные имеют фиксированные виды; все связи используют стабильные ID. Шаблон создания содержит общие поля и поля по типам изделий. Сохранять независимый снимок схемы в каждой карточке, чтобы изменения шаблона не меняли существующие украшения.

## Тема — первый этап UI

- Один MantineProvider в корне. Светлая молочная и тёмная коричневая палитры, режим auto по умолчанию. Акценты: приглушённый бордовый (по умолчанию), зелёный и охра. Простой читаемый шрифт для всего интерфейса.
- Семантические токены: фон, поверхность, основной/вторичный текст, граница, акцент, ошибка, фокус; единые отступы, радиусы и типографика.
- Конкретные значения цветов задаются только в модуле темы. Компоненты используют токены.
- Уточнение архитектуры по аудиту: переносимые настройки оформления хранить в IndexedDB как источник истины и восстанавливать одной транзакцией с коллекцией. localStorage использовать только как производный кэш для первого отображения, синхронизировать после чтения базы и после импорта. Отказ обновления кэша не должен терять настройки или делать восстановление данных частичным. В задаче 01 доступ к настройкам изолировать, подключение канонического хранилища завершить в задаче 02.
- Проверить контраст и все состояния для каждой поддержанной комбинации темы и акцента.
- Сначала каркас и демонстрация полей/кнопок/диалогов в обеих темах, затем функциональные экраны.
- Навигация — сайдбар с коллекцией, подкатегориями и настройками. Основная версия мобильная, также базовый адаптив для десктопа. Предложение для прототипа: выдвижное меню на мобильном, постоянная панель слева на широком экране. В коллекции закрываемая плашка установки, в настройках постоянная ссылка на инструкцию.

## Данные и фотографии

Задача 03: Dexie v3 добавляет items и photos, включает обязательный тип в существующих шаблонах и добавляет начальные пробы без перезаписи прежних справочников. У украшения revision, упорядоченные photoIds (первое — обложка), числовые сохранённые вес/размер; Blob хранятся отдельно и читаются только для видимых фото. Подготовка файлов выполняется до транзакции; запись карточки, добавление/удаление фото атомарны. Одна форма обслуживает создание и редактирование; состояние черновика локальное. Просмотр, редактор фотографий, рендер полей и фильтры — отдельные компоненты. Общий state manager и новые зависимости не требуются.

Карточки и Blob фотографий хранятся отдельно в IndexedDB. Метаданные коллекции читаются без массовой загрузки оригиналов. Фото подгружаются по мере появления в области просмотра; object URL освобождаются. На первом этапе не создавать уменьшенные копии без отдельного согласования. Проверить память при работе с оригиналами на телефоне.

Сохранение/удаление записи с фото — транзакция. Все миграции версионируются; обновление приложения не удаляет базу. Ошибки квоты и доступа к хранилищу обрабатываются явно.

Перед изменением схемы написать проверку миграции с предыдущей версии. Не допускать молчаливой потери изменений при одновременном редактировании в двух вкладках; в задаче 02 реализована проверка revision внутри транзакции для шаблона, справочников и оформления.

## Импорт и экспорт

Предложение: manifest.json с formatVersion и метаданными плюс photos/<id> в ZIP. Полная проверка структуры, уникальности ID, ссылок, типов, размеров распаковки и версии до записи. Лимиты определить по измерениям на iPhone, не вводить молча. Замена базы выполняется одной транзакцией после подтверждения. Проверить экспорт→импорт сравнением данных и байтов фото.

Экспортировать согласованный снимок, чтобы изменение/удаление карточки во время подготовки архива не оставило потерянных ссылок на фото. Во время замены исключить конкурирующие записи. Отказ квоты должен откатывать замену вместе с переносимыми настройками. После восстановления сбросить производные UI-кэши, не относящиеся к новой коллекции. Проверять отмену системного сохранения файла и не объявлять её успешным экспортом без подтверждения доступного API.

Согласован сценарий переноса на другой телефон через полное восстановление с заменой текущих данных; объединение не требуется. Экспорт не меняет исходную коллекцию. При непустом целевом хранилище явно сообщать о замене и запрашивать подтверждение. Резервная копия включает текущий шаблон создания и снимки схем всех старых карточек. ZIP-библиотеку загружать при использовании экспорта/импорта. Способ сохранения и открытия файлов проверить через системный интерфейс iOS; не полагаться только на File System Access API. Проверить перенос между двумя устройствами, а также отмену и восстановление поверх непустой коллекции.

## PWA и проверка платформы

Все необходимые ресурсы поставляются с приложением, без внешних шрифтов/CDN. Service worker кэширует оболочку; пользовательская коллекция хранится в IndexedDB. Офлайн-готовность показывается после завершения подготовки. Не выполнять автоматический reload с несохранённой формой.

Playwright WebKit полезен для автоматизации, но не заменяет Safari и установленную PWA на iPhone. На устройстве проверить установку, авиарежим, закрытие/повторный запуск, камеру, фото из галереи, экспорт в «Файлы», восстановление, клавиатуру и обновление приложения.

Приёмка расширена AC-14–AC-21; для первой версии базы проверяются создание/повторное открытие и откат, для следующих — миграции с предыдущей версии. Не вводить искусственную миграцию из несуществующей старой базы.

Конструктор дополнительных полей остаётся отдельной формой.

### Реализованный слой задачи 02

Подключены Dexie, Zod и fake-indexeddb; реактивные подписки используют liveQuery с сохранением последнего успешного состояния при ошибке. Схема version(2) мигрирует прежние поля в enabled=true; удалённые optional встроенные поля возвращаются с enabled=false. Скрытые поля исключаются из новых снимков, required действует только для видимых. Checkbox справа управляет каждым полем, разделы редактора свёрнуты по умолчанию, перестановка удалена. Начальная схема version(1) содержит только templates, dictionaries и settings; таблицы карточек и фотографий относятся к задаче 03. CreationTemplate хранит fields, область каждого поля задаётся scope; справочник использует DictionaryEntry.kind и sizeKind для типов изделий.

Инициализация выполняется отдельно от реактивных read-only запросов. Оформление читается из IndexedDB, кэш используется для начального отображения и однократного переноса; отдельная ошибка кэша не откатывает успешную запись. Конфликт ревизий и сбой записи сохраняют черновик, конкурентные обновления оформления обрабатываются без отката к устаревшей ревизии.

Типы фиксированы, всегда видимы и обязательны. Проба выбирается из справочника. Схема version(3) добавляет items и photos, восстанавливает доступность встроенных типов и поля типа, добавляет начальные пробы. Карточки и оригиналы сохраняются одной транзакцией с проверкой revision. Размер меняет формат при смене типа, остальные поля исторического снимка сохраняются. Редактор и просмотр карточки загружаются отдельными чанками; чтение Blob ограничено видимыми фотографиями.

## Задача 04 — реализация 2026-11-23
Согласованный объём и приёмка — [spec.md](spec.md#реализация-переноса-и-pwa--2026-11-23). Отдельный валидатор копии и репозиторий экспорта/замены; интерфейс переноса в настройках. ZIP готовится вне транзакций записи; полная замена выполняется атомарно. Настройки и цены включены в копию. PWA кэширует локальные ресурсы production-сборки и предлагает управляемое обновление. Браузерные проверки выполняются на preview; физические устройства и публикация остаются открытыми.

Мобильная форма: локальный CSS минимального шрифта полей, управляемое раскрытие MultiSelect материалов. Категория остаётся в App как единый источник; CollectionPage передаёт её в сводку фильтров и вызывает сброс через callback. Контракт базы не меняется.

Сохранение фото: PhotoSaveOptions уведомляет PhotoSaveMenu об успешной передаче оригиналов через callback; используется существующее закрытие с восстановлением фокуса. Отмена и ошибка не закрывают диалог.
