# Правила разработки Jewellery Box

## Работа по спецификациям

- Источник продуктовых требований: [основная спецификация](docs/specs/001-jewellery-catalog/spec.md). Связанные документы: [план](docs/specs/001-jewellery-catalog/plan.md), [модель данных](docs/specs/001-jewellery-catalog/data-model.md), [задачи](docs/specs/001-jewellery-catalog/tasks.md), [решения и открытые вопросы](docs/specs/001-jewellery-catalog/review.md). Учитывать статус «подтверждено», «предложение», «открытый вопрос».
- Каждая задача должна ссылаться на правила проекта, основную спецификацию, план, модель данных, реестр вопросов и список задач. Зависимости между задачами оформлять ссылками. При перемещении документов проверять относительные ссылки; общие требования не копировать в задачи вместо ссылки на источник.
- Для нового поведения сначала обновлять спецификацию и критерии приёмки, затем план/задачи и код. Не превращать предположения в согласованные требования.
- Не добавлять функции вне согласованного объёма. Прямые указания пользователя имеют приоритет.

## Архитектура и типы

- Использовать TypeScript strict. Не применять any, @ts-ignore и отключение lint вместо исправления проблемы; необходимое исключение объяснять локально.
- Проверять внешние данные на границе: импорт, браузерное хранилище, пользовательские поля. Типы TypeScript не заменяют runtime-валидацию.
- Доменные правила не зависят от React и выбранного UI-кита. Доступ к IndexedDB и миграции сосредоточены в data, UI использует операции/хуки этого слоя.
- Хранить состояние близко к месту использования. Новую зависимость добавлять для конкретной задачи с объяснением, учитывая размер и поддержку iPhone.
- Не создавать абстракции, универсальные фабрики и обёртки над каждым UI-компонентом без реальной необходимости.

## Интерфейс

- Одна система компонентов и одна тема. Цвета — через семантические токены; локальные стили — CSS Modules. Общие размеры и интервалы брать из темы.
- Каждое изменение UI проверять в светлой и тёмной темах, с узким экраном и сенсорным вводом.
- У полей должны быть подписи, у кнопок с иконками — доступные имена. Сохранять управление фокусом и поддержку клавиатуры.
- Показывать ошибки сохранения; не закрывать заполненную форму при ошибке. Не использовать молчаливые catch.

## Данные и приватность

- Не добавлять backend, облачную синхронизацию, телеметрию или внешнюю загрузку фото без явного изменения требований.
- Не логировать пользовательские фото, заметки и полный импорт. Не коммитить личные данные и реальные резервные копии.
- Изменения схемы — через версионированные миграции. Запрещено очищать пользовательскую базу как способ исправления ошибки.
- Связанные изменения записи и фото выполнять атомарно. Импорт проверять до изменения базы.
- Не сжимать и не перекодировать оригиналы без согласованного изменения требований. Освобождать object URL.

## Проверки и поддерживаемость

- Имена кода — английские; пользовательский текст — на согласованном языке. Комментарии объясняют причины и ограничения.
- Один модуль решает связную задачу; не раздувать App.tsx логикой хранения, форм и каталога.
- До завершения изменения запускать релевантные проверки. Для кода обязательны build и lint; после добавления тестового стека — тесты затронутого поведения.
- Тестировать прежде всего правила динамических полей, фильтры, атомарность, миграции, импорт/экспорт и сохранность данных. Не писать тесты, копирующие реализацию.
- Проверки PWA проводить на production-сборке. Playwright WebKit не считать доказательством работы на реальном iPhone.
- Форматирование автоматизировать Prettier; lock-файл обновлять вместе с зависимостями. Не менять посторонние файлы в рамках задачи.
- В отчёте указывать результат, выполненные проверки и оставшиеся ограничения. Не заявлять о проверках, которые не выполнялись.
